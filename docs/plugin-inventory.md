# PluginsStem Plugin Inventory

Generated by static analysis of the repository, reconciled against the Dataverse
step/image export on 2026-09-28. Scope: the `PluginsStem` C# project (single assembly,
`PluginsStem.dll`, `AssemblyName=PluginsStem`, `TargetFrameworkVersion=v4.7.1`, defined in
`PluginsStem/PluginsStem.csproj`).

## Method & data sources

- **Code side:** grepped for `IPlugin`, `Execute(IServiceProvider`, and any base classes.
  All 24 non-AssemblyInfo `.cs` files in `PluginsStem/` (25 plugin-shaped classes — one
  file, `CreateConnectionsContact.cs`, also defines a shared `AccountDto`) were read in
  full. No `[CrmPluginRegistration(...)]` attributes, `spkl.json`, or `*.crmregister` files
  exist anywhere in this repository — there is **no** in-source registration.
- **Dataverse side:** two exports were supplied as a companion to the code:
  - `Active_Steps.csv` — an org-wide dump of every **active** (enabled) plugin step
    (`assembly, plugin_type, step_name, message, entity, stage, mode, rank,
    filteringattributes`). Filtered to `assembly == "PluginsStem"`: **29 active steps**
    across the 25 plugin classes.
  - `Images.csv` — an org-wide dump of registered step images (`plugin_type, step_name,
    imagetype, entityalias, attributes`). Filtered to `plugin_type` starting with
    `PluginsStem.`: **11 images**. Note: the `attributes` column is `NULL` on **every**
    one of these 11 rows (not just for PluginsStem) — the export does not capture
    per-image attribute lists, so "does the image carry the field the code needs" could
    not be confirmed column-by-column and is flagged wherever it matters.
  - Because the export is titled *Active* Steps, a plugin type with **no rows at all** is
    either never registered or currently has all its steps disabled — both read as "dead
    in production" from Dataverse's point of view. Where an **image** exists for a plugin
    with no active step (see `DeactivateDBSRecords`), that step still exists in the org
    (images cascade-delete with their step) but is disabled.
- Stage/mode legend used below: stage `20` = Pre-operation, `40` = Post-operation (no
  `10`/Pre-validation steps exist for this assembly); mode `0` = Synchronous, `1` =
  Asynchronous. `rank` was `1` on every single PluginsStem row — not a meaningful
  differentiator here except where multiple plugins share a step (noted below).
- Only one assembly is present, so no per-assembly grouping was needed.

## Reconciliation summary — what actually runs in Dataverse today

This is the single most important output of joining the CSVs: **five of the 25 plugin
classes cannot run at all under the current registration**, and several that do run are
wired to the wrong trigger. Ordered by severity:

1. **Two plugin classes have no registration anywhere in the org and are fully dead:**
   `ContactSyncDBSFields` and `FillPrimaryNameColumn`. Neither appears in `Active_Steps.csv`
   or `Images.csv` under any spelling. `SyncAreaOfExpertiseChoices` is also absent — expected,
   since it doesn't implement `IPlugin` and so could never have been registered in the
   first place (this cross-check *confirms* Flag O-1 below rather than adding a new one).

2. **`DBSExpiryDate.cs` is orphaned — the message it expects is bound to something else
   entirely.** The custom message `sam_DBSExpiryDate` *is* registered and active, but its
   plugin type is `Microsoft.Crm.ObjectModel.SyncWorkflowExecutionPlugin` (Dataverse's
   built-in handler for a classic Workflow/Action definition), **not**
   `PluginsStem.DBSExpiryDate`. Whatever calls this custom action today runs a Dataverse
   workflow, not this C# code. This plugin class is compiled into the assembly but
   unreachable.

3. **`DeactivateDBSRecords` has a registered step and image, but the step is disabled.**
   `Images.csv` shows a `PreImage` on "Update of sam_dbs" for this plugin, which can only
   exist if the step itself exists — yet it's absent from `Active_Steps.csv`. The step
   exists in the org, switched off.

4. **`CalculateActivityDuration` and `CalculateActualDuration` are both live on `Update` of
   `sam_ambassadoractivity`, on different stages, and can re-trigger each other.**
   `CalculateActivityDuration` runs **Pre-operation (stage 20)**, synchronous, with **no
   filtering attributes** (fires on *any* field change) and writes `actualdurationminutes`
   directly onto `target` in place. `CalculateActualDuration` runs **Post-operation (stage
   40)**, synchronous, filtered to `actualend,actualstart` only, and does its own explicit
   `service.Update()` call. Neither plugin checks `context.Depth`. On an update that
   changes `actualstart`/`actualend`: stage-20 `CalculateActivityDuration` computes and
   in-place-sets the duration; the operation commits; stage-40
   `CalculateActualDuration` then fires (its filter is satisfied) and issues its own
   `Update()` — which re-enters the whole synchronous pipeline (stage 20 runs again) before
   returning. Confirmed real duplicate registration, not just duplicate code — highest
   priority to resolve (retire one of the two).

5. **`SetInductionStatus` and `CalculateInductionStatus` are both live on `Update` of
   `contact` and overlap.** `CalculateInductionStatus` is synchronous with no filtering
   attributes (fires on *any* contact edit). `SetInductionStatus` is **asynchronous**,
   filtered to exactly the four boolean fields
   (`sam_ambassadoragreementsigned,sam_inductionvideowatched,sam_profilecompleted,
   sam_safeguardingcoursecompleted`) — critically, **`sam_inductionstatus` itself is not
   in that filter list**, so `SetInductionStatus`'s second branch
   (`handleInductionDate`, gated on `entity.Contains("sam_inductionstatus")`) can only run
   in the rare case `sam_inductionstatus` changes in the *same* update as one of the four
   booleans. In ordinary use, `CalculateInductionStatus` already does the full job
   synchronously; `SetInductionStatus` then queues an async re-run of the same
   `sam_inductionstatus` recompute, and its date-handling branch is effectively
   unreachable. Looks like an incomplete migration between the two plugins.

6. **`PopulateActivityAmbassadorName` is only registered on `Create` — never `Update`.**
   The plugin's entire `MessageName == "Update"` branch, and its `PreImage` read, are dead
   code under current registration; no image is registered for it either (consistent with
   there being no Update step to attach one to).

7. **`UpdateActivityHoursFromAmbassadorStatus` is only registered on `Update` — never
   `SetState`.** The code explicitly branches on `context.MessageName == "SetState"`
   (reading `EntityMoniker`), but no `SetState` step exists in the export — that branch is
   dead code. Its registered `PreImage` on the Update step is also unused: the code always
   re-`Retrieve`s the record rather than reading any image.

8. **`UpdateContactLastActivityDate` is bound to the wrong entity on one of its two steps,
   and its Update path is unregistered.** Two async steps exist: "Create of
   `sam_activityambassador`" (correct — matches the code's entity guard) and "**Update of
   `sam_ambassadoractivity`**" — but the code immediately returns unless
   `target.LogicalName == "sam_activityambassador"`, so every firing of that second step is
   a guaranteed no-op. There is no "Update of `sam_activityambassador`" step at all, so the
   code's `Update` branch is unreachable too. As registered, this plugin only ever does
   anything on **Create** of `sam_activityambassador`.

9. **`PostActivityFeedback` has no image registered at all**, despite the code preferring
   `context.PostEntityImages["PostImage"]`. It always falls back to raw `Target`. Its one
   step is filtered on no attributes (fires on any `sam_activityfeedback` change), so an
   update that doesn't touch `statuscode`/`sam_contact`/`sam_activity` in the same call as
   the Completed-status transition will silently no-op. Also note the step's Dataverse
   display name is stale/misleading: `"PluginsStem.PostActivityFeedback: Update of
   sam_activityambassador (Profiled)"` — the *entity* column correctly says
   `sam_activityfeedback` (matching the code), only the human-readable label is wrong.

10. **Registered-but-unused images** (image exists in the export; the corresponding code
    never reads an image and instead re-`Retrieve`s or doesn't need one): `AmbassadorFillEmailAddress`
    (PreImage on `contact` Update — the `contact` branch reads only `Target`, never
    `PreImage`), `CalculateInductionStatus` (PreImage on `contact` Update — code
    re-`Retrieve`s), `UpdateActivityHoursFromAmbassadorStatus` (see #7). Harmless but worth
    cleaning up, and worth double-checking these aren't evidence the code *used to* read
    images and was refactored without updating the registration.

11. **Three plugins share the same step (Update of `sam_activityambassador`, stage 40,
    rank 1) with no execution-order guarantee:** `SetActivityAmbassadorHub`,
    `UpdateActivityAmbassadorCounts`, `UpdateActivityHoursFromAmbassadorStatus`. All
    three have `rank = 1`, so Dataverse does not guarantee their relative order. Given
    `UpdateActivityAmbassadorCounts` temporarily flips the parent activity through
    `SetState` (reopen/re-close) as part of its own execution, and
    `UpdateActivityHoursFromAmbassadorStatus`'s code is written expecting `SetState` events
    on the *ambassador* (which, per #7, isn't actually wired), confirm the three don't need
    a defined rank order.

12. **Everything else checks out.** The following plugins' registered steps/images match
    what the code expects with no discrepancy: `CalculateActualDuration` (aside from #4),
    `CalculateProfileCompleted`, `CreateActivityFromOffer`, `CreateActivityFromOfferWeb`,
    `CreateConnections`, `CreateConnectionsContact`, `ExpireActivityFeedback`,
    `PostActivityProcess`, `PreActivityProcess`, `SetActivityAmbassadorHub`,
    `UpdateActivityAmbassadorCounts`, `UpdatePreparationHoursFromFeedback` (its correctness
    still hinges on the PreImage actually carrying `statuscode` — the export can't confirm
    per-image attributes, so this one is worth a manual spot-check in the platform given
    how load-bearing that guard is).

## Original code-only flags (from static analysis, before the Dataverse export)

These are retained from the first pass; several are now resolved/confirmed by the
reconciliation above (cross-referenced), others still stand on their own.

**O-1. `SyncAreaOfExpertiseChoices` does not implement `IPlugin`.**
(`SyncAreaOfExpertiseChoices.cs:14`) `public class SyncAreaOfExpertiseChoices` has an
`Execute(IServiceProvider)` method but no `: IPlugin`. Confirmed by the export: it has zero
registrations anywhere, consistent with being unregisterable as written. Needs a source fix
(add `: IPlugin`) or confirmation it's intentionally unused.

**O-2. Likely bug: `FillPrimaryNameColumn.cs:108`** —
`partnerUserToUpdate["name"] = partnerUserToUpdate;` assigns the `Entity` object itself to
the `name` attribute (should almost certainly be `fullNamePartnerUser`). Moot in production
right now since the whole class has no active registration (see reconciliation #1), but
worth fixing before it's ever wired up.

**O-3. Commented-out code / dead branches**, left in place rather than removed:
- `PostActivityProcess.cs:117-133` — an entire "confirmed rule first → Did Not Run" branch
  is commented out (superseded by `SetActivityStatus`, but left inline).
- `PostActivityProcess.cs:171-176` — commented-out `RecalculateHoursForAmbassador` calls
  for `interest`/`suggested` lists.
- `ExpireActivtyFeedback.cs:54-60, 75-88` — commented-out direct-`Entity` update code,
  superseded by `SetStateRequest`, left alongside the live code.
- `FillPrimaryNameColumn.cs:176-180` — commented-out `amb_user` update block.
- `DBSExpiryDate.cs:23-24` — commented-out `Target` read that is no longer used, consistent
  with this plugin being a custom-message handler that never reads `Target`.

**O-4. Two near-duplicate custom-API pairs.** `CreateActivityFromOffer` /
`CreateActivityFromOfferWeb` and `CreateConnections` / `CreateConnectionsContact` are
near-identical logic. Both members of both pairs are confirmed actively registered
(`sam_CreateActivityFromOffer` / `sam_CreateActivityFromOfferWeb` and
`sam_CreateConnections` / `sam_CreateConnectionsContact`), so neither is orphaned — this is
a maintenance-burden observation, not a dead-code one.

**O-5. Custom-API plugins have no source-visible parameter/response schema.**
`CreateActivityFromOffer`, `CreateActivityFromOfferWeb`, `CreateConnections`,
`CreateConnectionsContact` are confirmed via `Active_Steps.csv` to be registered as custom
messages (`sam_CreateActivityFromOffer` etc., "(all entities)", unbound). Their argument
schema, response schema, and Custom API definition itself still live entirely in Dataverse
metadata — there is no `.xml`/`.json` definition file in this repository.

## Detailed plugin reference

Every plugin below is in assembly **`PluginsStem.dll`** (`PluginsStem/PluginsStem.csproj`,
namespace `PluginsStem`). No plugin declares a constructor, so **Config: none** for all 25
(not repeated per entry below). "Registered steps" and "Images" are taken verbatim from the
Dataverse export (`Active_Steps.csv` / `Images.csv`, filtered to this assembly/plugin type);
"Code expects" is independent, derived purely from reading `Execute`.

### 1. AmbassadorFillEmailAddress

- **Class / file:** `AmbassadorFillEmailAddress` — `PluginsStem/AmbassadorFillEmailAddress.cs`
- **Base class:** `IPlugin` (direct)
- **Summary:** Keeps `amb_ambassador.amb_emailaddress` synchronized with the ambassador's
  linked `amb_user` email, and propagates `contact.emailaddress1` / `amb_user.amb_emailaddress`
  changes down to any linked `amb_ambassador` records.
- **Registered steps (Dataverse, active):**
  | Message | Entity | Stage | Mode | Filtering attributes |
  |---|---|---|---|---|
  | Create | `amb_ambassador` | 40 | Sync | `amb_userid` |
  | Update | `amb_ambassador` | 40 | Sync | `amb_userid` |
  | Create | `contact` | 40 | Sync | (none) |
  | Update | `contact` | 40 | Sync | (none) |
  | Create | `amb_user` | 40 | Sync | `amb_emailaddress` |
  | Update | `amb_user` | 40 | Sync | `amb_emailaddress` |
- **Images (Dataverse):** PreImage on Update `amb_user`; PreImage on Update `contact`.
  Attributes not captured in the export.
- **Code expects:**
  - `amb_ambassador`: Create **or** Update, if `amb_userid` present → copy linked
    `amb_user.amb_emailaddress`.
  - `contact`: Create/Update, requires non-blank `emailaddress1`; propagates to linked
    `amb_ambassador` via `amb_user`.
  - `amb_user`: Create/Update; reads `amb_emailaddress` from Target, falling back to
    `PreImage` on Update only if not on Target.
- **Reconciliation:**
  - `amb_ambassador`/`amb_user` filters match the code's own `entity.Contains(...)` guards.
  - The `contact` PreImage is **registered but unused** — the `contact` branch reads only
    `Target.emailaddress1`, never any image. (See flag #10.)
  - The `amb_user` filter on `amb_emailaddress` means the step only fires when that field
    actually changes, so `Target` will normally already carry it — making the code's
    `PreImage` fallback for `amb_user` Update effectively unreachable in ordinary use
    (low-severity; the fallback is harmless dead code, not a bug).
- **External dependencies:** `IOrganizationService.Retrieve`/`RetrieveMultiple`/`Update`
  only; no custom APIs, no HTTP calls, no shared helper classes.

### 2. CalculateActivityDuration

- **Class / file:** `CalculateActivityDuration` — `PluginsStem/CalculateActivityDuration.cs`
- **Base class:** `IPlugin` (direct)
- **Summary:** Pre-operation: syncs `scheduledstart`/`scheduledend` to the actual dates and
  computes `actualdurationminutes` — writes directly onto `target`, not via a separate
  `Update()` call.
- **Registered steps (Dataverse, active):**
  | Message | Entity | Stage | Mode | Filtering attributes |
  |---|---|---|---|---|
  | Update | `sam_ambassadoractivity` | **20 (Pre-operation)** | Sync | (none) |
- **Images (Dataverse):** PreImage on Update. Attributes not captured in the export.
- **Code expects:** `context.MessageName != "Update"` → return. Requires
  `target.LogicalName == "sam_ambassadoractivity"`. Reads `actualstart`/`actualend` from
  `target`, falling back to `PreImage`. If either is still null, returns without writing
  duration (may still have written scheduled dates).
- **Reconciliation:** No filtering attributes means this fires on **every** update to the
  activity, not just start/end changes — every activity edit re-syncs scheduled dates and
  recomputes duration. Combined with `CalculateActualDuration` (#3) being registered on
  the same entity/message at a later stage with a tighter filter, this is a confirmed
  double-registration risk — see reconciliation item #4 at the top of this document.
- **External dependencies:** none beyond plugin-context services; writes are made in-place
  on `target`, no explicit `service.Update()` call. Does not check `context.Depth`.

- **Summary:** Recomputes `actualdurationminutes` on an activity from
  `actualstart`/`actualend` and writes it via an explicit `service.Update()` call (contrast

- **Registered steps (Dataverse, active):**

  | Create | `sam_ambassadoractivity` | 40 | Sync | `actualend,actualstart` |

- **Images (Dataverse):** PreImage on Update. Attributes not captured in the export.

  falling back entirely to `PreImage` if the attribute isn't present at all on `target`.
  If either ends up null, returns without update.
- **Reconciliation:** Registered on the **same entity and message** as

### 6. ContactSyncDBSFields

- **Class / file:** `ContactSyncDBSFields` — `PluginsStem/ContactSyncDBSFields.cs`
- **Base class:** `IPlugin` (direct)
- **Summary:** When a `sam_dbs` record is created/updated, re-derives the linked contact's
  DBS status/certificate number/expiry date from that contact's most recent active
  `sam_dbs` record.
- **Registered steps (Dataverse, active):** **none.** No row for
  `PluginsStem.ContactSyncDBSFields` in `Active_Steps.csv` under any message/entity.
- **Images (Dataverse):** none.
- **Code expects:** requires `Target`; branches on `context.MessageName == "Create"` or
  `"Update"` (re-retrieves the `sam_dbs` record regardless of message to find its
  `sam_dbscontact`, then queries all active `sam_dbs` records for that contact and uses the
  **first result with no explicit ordering** — unlike `DeactivateDBSRecords`, which orders
  by `createdon desc`).
- **Reconciliation:** **This plugin has no active registration anywhere in the org.** As
