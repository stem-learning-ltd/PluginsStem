# PluginsStem Plugin Inventory

Generated by static analysis of the repository on 2026-09-22. Scope: the `PluginsStem`
C# project (single assembly, `PluginsStem.dll`, `AssemblyName=PluginsStem`,
`TargetFrameworkVersion=v4.7.1`, defined in `PluginsStem/PluginsStem.csproj`).

## Method & caveats

- **Step 1 (find plugins):** grepped for `IPlugin`, `Execute(IServiceProvider`, and any
  base classes. All 24 non-AssemblyInfo `.cs` files in `PluginsStem/` were read in full.
- **Step 2 (registration source):** searched for `[CrmPluginRegistration(...)]` attributes,
  `spkl.json`, and `*.crmregister` files. **None exist in this repository.** There is no
  in-source registration of steps, images, filtering attributes, stages, or modes anywhere
  in the codebase. Every "Registered steps" field below is therefore marked
  **`pending (Dataverse)`** — to be filled in once the Dataverse step-registration CSV is
  supplied. Nothing about rank, sync/async mode, stage, or filtering attributes is invented.
- **Step 3/4:** each plugin section documents what the *code* branches on/guards against
  (message name, entity, `context.Depth`), which image aliases/attributes it reads, config
  usage, and external dependencies, plus a Flags subsection.
- Only one assembly is present, so no per-assembly grouping was needed — all plugins below
  are in `PluginsStem.dll`.

## Flags for a second look

1. **`SyncAreaOfExpertiseChoices` does not implement `IPlugin`.** (`SyncAreaOfExpertiseChoices.cs:14`)
   `public class SyncAreaOfExpertiseChoices` has an `Execute(IServiceProvider)` method but no
   `: IPlugin` (contrast with every other class in the project). The Dataverse plugin
   registration tool requires the type to implement `Microsoft.Xrm.Sdk.IPlugin` to register
   it as a step. As written, this class cannot be registered/found by the registration tool —
   either it's dead code, mid-refactor, or was registered previously under a signature this
   snapshot broke. Needs a source fix (add `: IPlugin`) or confirmation it's intentionally
   unused before the Dataverse CSV is joined.

2. **Duplicate duration-calculation logic on the same entity.** `CalculateActivityDuration`
   and `CalculateActualDuration` (in `CalculateActualDurationActivity.cs`) both compute
   `sam_ambassadoractivity.actualdurationminutes` from `actualstart`/`actualend`, both read
   the same `PreImage` fallback pattern, and both would plausibly be registered on the same
   Update. `CalculateActivityDuration` also pre-op writes `scheduledstart`/`scheduledend`
   directly on `target` (implying a synchronous pre-operation step) while
   `CalculateActualDuration` does a *separate* `service.Update()` call (implying it runs
   post-operation or async). If both are registered on Update of `sam_ambassadoractivity`,
   confirm they aren't fighting each other or double-updating (one edits `target` in place,
   the other calls `Update()` explicitly, which would itself re-trigger plugins unless
   `Depth` is guarded — note neither of these two checks `context.Depth`).

3. **`CalculateInductionStatus` and `SetInductionStatus` overlap.** Both recompute
   `contact.sam_inductionstatus` and `stem_inductiondate` from the same four boolean fields,
   with slightly different code paths (one does everything unconditionally on Create/Update
   of `contact`; the other only on Update, gated by which attributes are present on `Target`).
   If both are registered on `contact` Update, verify they don't produce conflicting values
   or redundant recursive updates.

4. **Four plugins read no `Target` and check no message name at all** —
   `PostActivityProcess`, `PreActivityProcess`, `ExpireActivityFeedback`, and (via
   `PostEntityImages`/`Target` fallback only) `PostActivityFeedback` partially. The first
   three always run their full batch query regardless of what triggered them, which strongly
   suggests they are meant to run on a **recurring/scheduled trigger** (e.g. a Dataverse
   recurring system job, a Power Automate flow calling a custom action, or an "On demand"
   step) rather than a normal entity Create/Update step. Nothing in the source shows what
   registers or schedules them — flag for confirmation against the Dataverse step CSV
   (message name, whether it's a real entity step vs. an unbound/async recurring job).

5. **`FillPrimaryNameColumn` and `PostActivityFeedback` have no message-name guard.**
   Unlike most other plugins, these don't check `context.MessageName`, so if registered on
   more than one message (e.g. Create and Update, or Create/Update/Assign), they will run
   identically for all of them. Confirm intended registration matches this.

6. **Likely bug: `FillPrimaryNameColumn.cs:108`** —
   `partnerUserToUpdate["name"] = partnerUserToUpdate;` assigns the `Entity` object itself
   to the `name` attribute (should almost certainly be `fullNamePartnerUser`, matching every
   other branch in this method). This will throw or write garbage at runtime for the
   `amb_partneruser` case. Not a registration issue, but worth fixing regardless of what the
   Dataverse CSV shows.

7. **Nine plugins depend on a pre-image (or post-image) alias literally named `"PreImage"`
   / `"PostImage"`** and specific attributes on it. These registrations must be confirmed
   once the Dataverse export arrives — a missing or misconfigured image (wrong alias, wrong
   attributes, wrong message it's registered on) will silently degrade these plugins to
   "primary changed field only" behaviour instead of throwing:
   - `AmbassadorFillEmailAddress` — PreImage on `amb_user` Update, needs `amb_emailaddress`
   - `CalculateActivityDuration` — PreImage on `sam_ambassadoractivity` Update, needs `actualstart`, `actualend`
   - `CalculateActualDuration` — PreImage on `sam_ambassadoractivity` Create/Update, needs `actualstart`, `actualend`
   - `CalculateProfileCompleted` — PreImage on `contact` Create/Update, needs all 8 profile fields
   - `DeactivateDBSRecords` — PreImage on `sam_dbs` Update, needs `sam_dbscontact`
   - `PopulateActivityAmbassadorName` — PreImage on `sam_activityambassador` Update, needs `sam_ambassador`, `sam_ambassadoractivity`
   - `PostActivityFeedback` — PostImage on `sam_activityfeedback`, needs `statuscode`, `sam_contact`, `sam_activity`
   - `SetActivityAmbassadorHub` — PreImage on `sam_activityambassador` Update, needs `sam_ambassador`
   - `SyncAreaOfExpertiseChoices` — PreImage on `amb_areaofexpertise` Update/Delete, needs `amb_sqlid` (also blocked by Flag 1)
   - `UpdateActivityAmbassadorCounts` — PreImage on `sam_activityambassador` Update, needs `sam_ambassadoractivity`
   - `UpdateContactLastActivityDate` — PreImage on `sam_activityambassador` (message not explicit — Create/Update), needs `sam_ambassador`
   - `UpdatePreparationHoursFromFeedback` — PreImage on `sam_activityfeedback` Update, needs `sam_activityambassador`, `sam_preparationtimedecimal`, `sam_contact`, `statuscode`

8. **`DBSExpiryDate` and `ExpireActivityFeedback`/`PostActivityProcess`/`PreActivityProcess`
   look like they belong to the same "scheduled housekeeping" family** but only

   - `DBSExpiryDate.cs:23-24` — commented-out `Target` read that is no longer used (this
     plugin reads no `Target` at all; consistent with it being a custom-message handler).

10. **Two near-duplicate custom-API pairs** worth confirming aren't both registered
    (redundant maintenance burden even if harmless): `CreateActivityFromOffer` vs.
    `CreateActivityFromOfferWeb` (identical logic, presumably one for the model-driven app
    and one for the public website), and `CreateConnections` vs. `CreateConnectionsContact`
    (same pattern, different `record1id` entity). Confirm both members of each pair are
    genuinely still called from somewhere (web resources / portal) rather than one being
    orphaned.

11. **Custom-API-style plugins have no source-visible registration at all.**
    `CreateActivityFromOffer`, `CreateActivityFromOfferWeb`, `CreateConnections`,
    `CreateConnectionsContact` read named `InputParameters` (`recordID`, `name`,
    `description`, `activityType`, `connectToIDs`, `offerOwnerID`, `areasOfExpertise` /

## Detailed plugin reference

Every plugin below is in assembly **`PluginsStem.dll`** (`PluginsStem/PluginsStem.csproj`,
namespace `PluginsStem`). No plugin declares a constructor, so **Config: none** (no
secure/unsecure configuration is read anywhere in this project) is the same for all 25 and

### 1. AmbassadorFillEmailAddress

- **Class / file:** `AmbassadorFillEmailAddress` — `PluginsStem/AmbassadorFillEmailAddress.cs`
- **Base class:** `IPlugin` (direct)
- **Summary:** Keeps `amb_ambassador.amb_emailaddress` synchronized with the ambassador's
  linked `amb_user` email, and propagates `contact.emailaddress1` / `amb_user.amb_emailaddress`
  changes down to any linked `amb_ambassador` records.
- **Registered steps:** pending (Dataverse)
- **Code expectations:**
  - `entity.LogicalName == "amb_ambassador"`: on `Create` **or** `Update`, if
    `amb_userid` is present, retrieves the linked `amb_user` and copies its
    `amb_emailaddress` onto the ambassador (duplicate logic in the Create and Update
    branches).
  - `entity.LogicalName == "contact"`: only on `Create`/`Update` (returns otherwise);
    requires non-blank `emailaddress1`; finds `amb_user` records where
    `amb_ambassador_contact == contactId`, then for each, finds `amb_ambassador` records
    where `amb_userid == userId` and updates their email if different.
  - `entity.LogicalName == "amb_user"`: only on `Create`/`Update`; reads
    `amb_emailaddress` from Target, falling back to `PreEntityImages["PreImage"]` on
    Update if not present on Target; finds linked `amb_ambassador` records
    (`amb_userid == userId`) and updates their email if different.
- **Images used:** `PreEntityImages["PreImage"]` on `amb_user` (Update only) —
  attribute `amb_emailaddress`.
- **Config:** none.
- **External dependencies:** `IOrganizationService.Retrieve`/`RetrieveMultiple`/`Update`
  only; no custom APIs, no HTTP calls, no shared helper classes.

### 2. CalculateActivityDuration

- **Class / file:** `CalculateActivityDuration` — `PluginsStem/CalculateActivityDuration.cs`
- **Base class:** `IPlugin` (direct)
- **Summary:** On Update of an activity, syncs `scheduledstart`/`scheduledend` to the actual
  dates and computes `actualdurationminutes` — writes directly onto `target` (pre-operation
  style), not via a separate `Update()` call.
- **Registered steps:** pending (Dataverse)
- **Code expectations:** `context.MessageName != "Update"` → return. Requires
  `target.LogicalName == "sam_ambassadoractivity"`. Reads `actualstart`/`actualend` from
  `target`, falling back to `PreEntityImages["PreImage"]`. If either is still null, traces
  and returns without writing duration (but may still have written scheduled dates).
- **Images used:** `PreEntityImages["PreImage"]` — attributes `actualstart`, `actualend`.
- **Config:** none.
- **External dependencies:** none beyond the plugin-context services; writes are made
  in-place on `target` (relies on the platform's pre-operation pipeline to persist them),
  no explicit `service.Update()` call.
- **Flag:** see Flags #2 (duplicate of `CalculateActualDuration`); does not check
  `context.Depth`.

### 3. CalculateActualDuration

- **Class / file:** `CalculateActualDuration` — `PluginsStem/CalculateActualDurationActivity.cs`
  *(class name does not match file name)*
- **Base class:** `IPlugin` (direct)
- **Summary:** Recomputes `actualdurationminutes` on an activity from `actualstart`/`actualend`
  and writes it via an explicit `service.Update()` call (contrast with #2's in-place write).
- **Registered steps:** pending (Dataverse)
- **Code expectations:** requires `Target` to be an `Entity`; requires
  `target.LogicalName == "sam_ambassadoractivity"`; only acts on `context.MessageName ==
  "Create"` or `"Update"`. Reads `actualstart`/`actualend` from `target.Contains(...)`,
  falling back entirely to `PreImage` (not a null-coalesce per-field like #2 — if the
  attribute isn't on `target` at all it goes straight to `PreImage`, even on Create when
  there is no PreImage). If either end up null, returns without update.
- **Images used:** `PreEntityImages["PreImage"]` — attributes `actualstart`, `actualend`.
- **Config:** none.
- **External dependencies:** `IOrganizationService.Update` on `sam_ambassadoractivity`
  only.
- **Flag:** see Flags #2 (duplicate of `CalculateActivityDuration`); does not check
  `context.Depth`, and calling `service.Update()` from inside a plugin that may itself be
  triggered by Update risks re-entrant execution if depth isn't guarded elsewhere in the
  registration/other plugins on this entity.

### 6. ContactSyncDBSFields

- **Class / file:** `ContactSyncDBSFields` — `PluginsStem/ContactSyncDBSFields.cs`
- **Base class:** `IPlugin` (direct)
- **Summary:** When a `sam_dbs` record is created/updated, re-derives the linked contact's
  DBS status/certificate number/expiry date from that contact's most recent active `sam_dbs`
  record (an option-set value mapping, not simply copying the triggering record).
- **Registered steps:** pending (Dataverse)
- **Code expectations:** requires `Target` present and of type `Entity`; branches on
  `context.MessageName == "Create"` or `"Update"` (any other message returns). Always
  re-retrieves the `sam_dbs` record by ID to get `sam_dbscontact`, then queries all active
  (`statecode = 0`) `sam_dbs` records for that contact and uses the first one found (no
  explicit ordering in this query, unlike `DeactivateDBSRecords` which orders by
  `createdon desc` — worth confirming which record "wins" if a contact has multiple active
  DBS records).
- **Images used:** none — re-retrieves via `Retrieve`/`RetrieveMultiple`.
- **Config:** none.
- **External dependencies:** `IOrganizationService.Retrieve`/`RetrieveMultiple`/`Update`
  only. Private helper `getActiveDBSRecords` pages through results (Count 5000) but only
  the first entity is used.

- **Images used:** none (custom API — images don't apply to this message shape).
- **Config:** none.
- **External dependencies:** `Newtonsoft.Json` (`JsonConvert.DeserializeObject`) to parse
  `connectToIDs`; `IOrganizationService.Retrieve/Create` for `sam_offer`,
  `sam_ambassadoractivity`, `connection`, `sam_activityambassador`.
